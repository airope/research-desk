# Audit technique — 17 septembre 2026

> État constaté avant correction. Voir [les corrections et leur validation](audit-corrections-2026-09-17.md) pour l’état actuel.

## Avis

Le projet possède de bonnes protections de base et constitue une démonstration locale crédible. Il n'est pas encore prêt pour un hébergement partagé : la configuration, la maîtrise des ressources et le cycle de vie des données doivent être consolidés. Aucune clé API réelle en dur ni faille critique exploitable n'a été mise en évidence dans le périmètre examiné. Cela ne constitue pas une certification de sécurité.

Audit du code Django, des vues, permissions, imports, traitements PDF/LLM, recherches Elasticsearch, modèles, configuration, conteneurs et CI. Aucun code applicatif modifié. Le dépôt étant entièrement non suivi à cette date, les constats portent sur les fichiers présents, sans historique Git exploitable. Pas de test d'intrusion destructif, de test de charge ni d'audit des binaires Elasticsearch/PostgreSQL/Codex ou des images Docker.

P1 signifie à traiter avant une ouverture à d'autres utilisateurs ou un déploiement public ; P2 signifie défaut concret à corriger pour fiabiliser ou faire évoluer le produit. Ces priorités ne sont pas des scores CVSS.

## Constats prioritaires

### A1 — P1 — Le profil de production n'est pas défini de façon sûre

**Sources :** `srr/settings.py:7`, `srr/settings.py:52`, `srr/settings.py:93`, `compose.yaml`, `research/ai.py:29`.

DEBUG est activé par défaut et les secrets Django/PostgreSQL ont des valeurs de démonstration. Le refus de démarrer avec la clé Django de démonstration lorsque DEBUG=0 est une bonne protection, mais Compose impose DEBUG=1. Même en désactivant DEBUG, les cookies de session/CSRF ne sont pas marqués Secure et la configuration ne définit ni redirection HTTPS ni HSTS. Le serveur Compose est `runserver`. L'IA personnelle est délibérément conditionnée à DEBUG : ce chemin reste réservé au poste local.

**Impact :** réutiliser cette configuration pour héberger le service expose des informations de débogage et peut laisser les sessions circuler sans les protections attendues. Le déploiement actuel sur loopback limite ce risque ; il n'est pas présenté ici comme une exposition Internet existante.

**Correction :** profils développement/test/production explicites ; secrets obligatoires en production ; configuration HTTPS/cookies adaptée au proxy ; serveur de production ; contrôle de déploiement en CI. Prévoir un fournisseur IA de service distinct du mode abonnement personnel. Ne pas simplement supprimer la protection du mode local.

**Validation attendue :** démarrage refusé si un secret requis manque ; `check --deploy` sans avertissement non justifié sur le profil de production ; test des cookies et du proxy réel. Référence : [checklist officielle Django 5.2](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

### A2 — P1 — Les variantes de fichiers `.env` peuvent entrer dans Git et les images

**Sources :** `.gitignore:8`, `.dockerignore:4`, `Dockerfile:8`.

Seul le nom exact `.env` est exclu. Un futur `.env.local` ou `.env.production` contenant des secrets serait ajoutable à Git et copié dans l'image par `COPY . .`. Le test d'exclusion le confirme. Aucun fichier de ce type contenant un secret n'a été découvert : il s'agit d'une voie de fuite, pas d'une fuite constatée.

**Correction :** exclure `.env*` dans Git et Docker, avec exception explicite pour `.env.example` nettoyé ; ajouter une détection de secrets avant publication et en CI. Exclure aussi les caches inutiles du contexte Docker.

**Validation attendue :** les variantes sont ignorées ; l'exemple reste versionnable ; aucun secret de fixture ne se retrouve dans une image de test.

**Clarification :** `os.getenv` lit l'environnement, pas automatiquement un fichier `.env`. Le lancement Python actuel ne charge pas ce fichier ; l'interpolation Compose est un mécanisme distinct. Documenter le chargement ou ajouter un chargeur limité au développement. En production, des variables injectées ou un gestionnaire de secrets conviennent. Les URL fixes INSPIRE/arXiv ne sont pas des secrets : leur contrôle explicite participe à la protection des requêtes sortantes.

### A3 — P1 — Les vues coûteuses et la connexion n'ont pas de limitation adaptée

**Sources :** `srr/settings.py:79`, `srr/urls.py`, `research/views.py:46`, `research/views.py:171`, `catalogues/views.py`.

Le throttle anonyme de Django REST Framework ne protège pas les vues Django classiques ni la connexion. La création de dossiers et les recherches ne disposent pas de quotas par utilisateur ou de plafond global de file d'attente. Empêcher deux actions simultanées sur un dossier ne limite pas la création de plusieurs dossiers.

**Impact :** tentatives répétées de connexion et consommation disproportionnée de ressources par un compte. L'IA est actuellement réservée au propriétaire configuré ; ce n'est pas un endpoint LLM ouvert aux anonymes.

**Correction :** limitation des échecs d'authentification ; quotas de recherches et de travaux simultanés ; budget IA ; admission contrôlée dans la file ; état de limitation partagé entre processus.

**Validation attendue :** dépassement rejeté avant l'appel externe, compteurs cohérents avec plusieurs workers, autres utilisateurs toujours servis.

### A4 — P2 — Lire des résultats Elasticsearch réindexe tout le corpus

**Sources :** `research/views.py:83`, `research/search_index.py:74`, `research/search_index.py:83`, `research/search_index.py:110`.

Chaque recherche de passages tente de créer l'index, réécrit les passages avec `refresh=wait_for`, puis effectue une recherche distincte pour chaque article, jusqu'à vingt. Une consultation GET déclenche donc des écritures et attend l'indexation dans le processus web.

**Impact :** latence et charge d'écriture répétées pour un corpus inchangé ; saturation des workers web ; besoin de droits d'écriture pour le chemin de consultation.

**Correction :** indexer au changement des sources dans un worker, conserver l'état d'indexation, utiliser un client de lecture pour les consultations, regrouper les recherches lorsque pertinent.

**Validation attendue :** deux recherches sur un même corpus ne produisent aucun nouvel appel bulk ; la mise à jour des sources déclenche une seule indexation ; erreurs d'index visibles sans bloquer indéfiniment la page.

### A5 — P2 — Les anciennes générations Elasticsearch ne sont pas purgées

**Source :** `research/search_index.py:56`.

Le digest de tout le corpus entre dans l'identifiant de chaque passage. Ajouter un article change aussi les identifiants des articles inchangés. Les nouvelles lignes sont indexées, mais les anciennes ne sont pas supprimées. Les filtres de corpus empêchent de les restituer : le problème constaté concerne le stockage et le cycle de vie, pas une fuite interutilisateurs.

**Impact :** croissance de l'index à chaque évolution, conservation de données devenues inutiles, statistiques de pertinence influencées par les anciennes copies.

**Correction :** identifiants/revisions par document ou générations explicites avec nettoyage après publication ; purge associée à la suppression du dossier ; politique de rétention et reconstruction documentées.

**Validation attendue :** plusieurs modifications successives ne laissent que les générations conservées volontairement ; une suppression nettoie aussi l'index.

### A6 — P2 — Les textes sont dupliqués dans des JSON chargés et réécrits trop largement

**Sources :** `research/models.py:19`, `research/jobs.py:23`, `research/jobs.py:234`, `research/views.py:68`, `research/views.py:334`.

Sources de travail, sources du rapport et versions historiques embarquent les textes dans le même dossier. La liste d'accueil charge les objets complets. Les mises à jour de progression chargent et sauvegardent aussi ces JSON, même pour un simple événement. Avec vingt articles pouvant chacun contenir 150 000 caractères extraits et plusieurs versions, cela représente potentiellement des dizaines de millions de caractères par dossier ; c'est une estimation de structure, pas une mesure de charge réalisée.

**Impact :** mémoire, lectures, écritures et sauvegardes croissent avec le texte et l'historique, y compris pour les opérations simples.

**Correction :** documents et preuves immuables référencés par les versions ; événements séparés ; requêtes de liste/statut limitées aux colonnes utiles ; mises à jour ciblées. Conserver la traçabilité des versions, sans recopier systématiquement les documents.

**Validation attendue :** accueil et polling ne sélectionnent plus les textes ; ajouter une version n'en duplique pas le contenu ; mesurer taille des données et temps de réponse sur un corpus représentatif.

### A7 — P2 — Le parseur PDF est borné en temps mais pas isolé des secrets

**Sources :** `research/fulltext.py:105`, `research/pdf_extract.py:14`.

Le sous-processus reçoit les PDF externes avec un délai de 30 secondes et des limites de ressources, mais hérite de l'environnement complet du worker, de son identité système et de ses accès. L'appel ne fournit pas `env`. Une séparation en processus n'est pas une sandbox de sécurité.

**Impact :** en cas de vulnérabilité du parseur, les credentials et fichiers accessibles au worker le seraient également. Aucun exploit du parseur n'a été identifié et le scan des dépendances n'en signale pas : c'est une lacune de confinement.

**Correction :** environnement minimal, répertoire dédié, utilisateur non privilégié, système de fichiers restreint et réseau coupé dans une isolation effective. Nettoyer seulement les variables ne protège pas les fichiers accessibles au même utilisateur.

**Validation attendue :** le parseur ne reçoit aucun secret de service, ne peut pas ouvrir les fichiers privés du worker ni effectuer une connexion réseau ; limites réellement appliquées sur l'environnement cible.

### A8 — P2 — Les délais réseau et le débit ne bornent pas complètement un travail

**Sources :** `research/fulltext.py:52`, `research/fulltext.py:81`, `research/fulltext.py:95`, `research/jobs.py:34`.

`timeout=25` ne signifie pas que tout téléchargement finit en 25 secondes : HTTPX limite notamment l'attente entre lectures. Un flux lent qui progresse peut garder un worker occupé longtemps malgré la limite de taille. La régulation arXiv utilise un verrou local au processus et ne coordonne donc pas plusieurs workers. Référence : [timeouts HTTPX](https://www.python-httpx.org/advanced/timeouts/).

**Impact :** travaux de durée mal bornée, débit externe multiplié en ajoutant des workers, possible incohérence avec le seuil de détection des travaux abandonnés. Les protections par run_id empêchent les écritures périmées mais n'arrêtent pas le calcul déjà lancé.

**Correction :** échéance totale propagée aux opérations et annulation effective ; coordination du débit entre workers ; heartbeat indépendant des étapes longues.

**Validation attendue :** un serveur simulant un flux lent est arrêté à l'échéance totale ; plusieurs workers respectent un même débit ; un travail vivant n'est pas déclaré abandonné pendant une opération autorisée.

### A9 — P2 — Compose ne démarre pas le worker du produit de recherche

**Sources :** `compose.yaml`, `compose.search.yaml`, `.github/workflows/ci.yml`.

Le service worker exécute la commande historique `worker`, pas `research_worker`. Le service Elasticsearch optionnel ne configure pas à lui seul le backend et les credentials de l'application. Le parcours actuellement utilisé dépend donc du lancement manuel de composants supplémentaires ; la CI ne valide pas cette composition complète.

**Impact :** quelqu'un qui clone et démarre uniquement Compose peut avoir une interface accessible et des recherches qui restent en attente. Le mode IA personnelle nécessite en outre le runtime local et son authentification.

**Correction :** fournir un chemin d'installation complet et explicite, avec worker de recherche, configuration du moteur et contrôles de santé ; distinguer la démo personnelle du déploiement serveur. Ajouter une vérification d'intégration avec Elasticsearch réel et fournisseur IA simulé, sans credentials personnels en CI.

**Validation attendue :** depuis un environnement vierge, les instructions permettent de créer un dossier et d'obtenir un résultat ; les composants absents sont signalés clairement ; sauvegarde et restauration vérifiées.

### A10 — P2 — Les transitions et contrats de recherche restent trop implicites

**Sources :** `research/views.py:171`, `research/jobs.py:67`, `research/investigation.py:28`, `research/models.py`.

Les vues d'action et l'exécuteur combinent validation, transitions d'état et appels de fournisseurs. Les états sont des chaînes libres ; plusieurs contrats circulent sous forme de dictionnaires et de clés internes. Modifier une étape oblige à connaître simultanément la vue, le worker et le format des sources.

**Impact :** risque de divergences et coût de maintenance à mesure que de nouvelles actions IA ou de nouveaux fournisseurs sont ajoutés. Ce constat n'établit pas un contournement actuel des contrôles d'accès.

**Correction :** extraire progressivement les commandes et transitions métier, typer les contrats de données, centraliser les budgets et statuts, maintenir des adaptateurs INSPIRE/LLM/index séparés. Pas besoin de transformer l'application en microservices.

**Validation attendue :** transitions invalides rejetées par le service métier, tests indépendants de HTTP, fournisseur simulable, tests d'annulation et de concurrence conservés.

## Protections déjà présentes à conserver

- Filtrage des dossiers par propriétaire et contrôles d'accès des catalogues privés ; protections CSRF et authentification Django. Les références publiques sont intentionnellement publiques.
- ORM et requêtes SQL constantes/paramétrées dans les chemins examinés ; absence d'usage identifié de shell=True ou d'évaluation de code utilisateur.
- Échappement des templates et neutralisation des cellules CSV pouvant être interprétées comme formules.
- Téléchargements limités à des dépôts HTTPS autorisés, validation des redirections, plafonds de taille et d'extraction.
- Adaptateur IA local utilisant des arguments de subprocess et un environnement restreint ; sortie structurée et validation des références ; nombre d'actions borné. Une citation existante ne garantit toutefois pas la justesse scientifique de l'interprétation.
- Verrous transactionnels et identifiant d'exécution empêchant qu'un ancien travail publie après annulation.
- Credentials Elasticsearch locaux hors code, fichiers en 0600 et clé limitée à l'index ; service local authentifié.

Les valeurs de démonstration dans les fixtures, la CI ou `.env.example` sont acceptables tant qu'elles restent explicitement non productives. Il n'est pas nécessaire de rendre configurable chaque constante métier ou URL autorisée.

## Ordre recommandé

1. Fermer les voies de fuite de secrets et définir les profils d'exécution (A1–A2).
2. Ajouter les limites de consommation et le confinement des traitements externes (A3, A7–A8).
3. Sortir l'indexation des consultations et traiter la rétention (A4–A5).
4. Réduire la duplication des données et formaliser les transitions (A6, A10).
5. Livrer un démarrage reproductible et une intégration complète en CI (A9), puis mesurer sur un jeu de données réaliste.

Le catalogue historique comporte aussi un verrou global pour certaines écritures (`records/services.py:41`) et des calculs de candidats qui parcourent la sélection (`catalogues/services.py:210`). Ces choix bornent sa concurrence ; les revoir sur la base de mesures si ce parcours redevient central. Aucun chiffre de capacité utilisateurs n'est justifiable sans test de charge.
